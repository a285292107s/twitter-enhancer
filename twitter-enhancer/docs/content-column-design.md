# 内容列设计提案：版心、媒体与内容语义

标本：`https://x.com/Sena_8ito/status/2099373351697523063?sort_replies=recency`
（SENA 8ito，正文 = 6 个 emoji，4 张竖图横向轮播，45 条回复）
实测环境：headless Chromium，1440×900 / 1280×720，仓库 `x-te-e2e` 持久登录态，
`dist` 产物经 addInitScript 注入（与 `npm run e2e:real` 同一路径）。日期 2026-09-14。

**状态：已实现**（2026-09-14）。第 4 节的规范按此落地，实际实现与提案的偏差见第 8 节；
第 5 节的三条裁决已按「默认 fit」执行。
**2026-09-16 变更**：第 4.3 节的「内容语义分层 / 短帖大字号」按用户要求移除（正文回到 X 原生字号），
版心成为唯一的正文级排版手段；版心令牌退回静态 764px（原由正文 72ch 的实测值覆盖）。

## 0. 结论摘要

1. 现在的问题不是「不好看」，是**列宽变了、版心没变**：主列 600 → 980（+63%），
   而正文/元信息/操作栏/排序行的左右边界被一起拉到 946px，只有正文被 `72ch` 拦住。
   结果：操作栏 6 个图标均分 946px、昵称行的「…」离名字 900px，页面读起来「被拉长」。
2. **多图轮播被我们改坏了**：`tweetPhoto` 每格 16px 圆角 + 6px 缝 = 「N 张圆角卡」；
   X 原生是**一块媒体切片**（外框直角、内缝、无独立圆角）。这是纯 CSS 层的视觉倒退，
   一条规则就能修好，收益最大。
3. **竖长多图在宽列下反而更小**：1440 下每格 291×534 = 原图（372×680）的 0.78 倍，
   而 X 原生 600 列下是 334×613。高度预算与宽度扩张互相打架，且右侧永远露 69px 的半格。
4. **方图/横图单图会被纵向压扁**：`/home` 实测 896×540，原图 900×895（比例 1.005 → 1.66），
   容器与 `img` 都是 `object-fit: fill`。X 自己的单图策略是「限高、等比、宽度自适应」
   （竖图实测 236×510，比例与原图一致），这才是该抄的作业。
5. **内容语义没被识别**：这个帖子的正文 `textContent` 长度为 0、只有 6 个 emoji `img`，
   却按 16px/1.5 的正文段落排版。短帖、emoji 帖、长文帖、纯图帖读起来应该不一样 ——
   这是「高端」与「AI 味」的分水岭：风格统一 ≠ 排版统一。

## 2. 诊断：为什么现在读起来「廉价 / AI 味」

每一条都能落到具体数值上，不是审美偏好。

- **P1 只拉宽不给版心。** 946px 的操作栏、876px 的排序行间距、昵称行右侧孤零零的「…」。
  宽列的正确用法是把多出来的宽度变成**留白**，不是把元素摊开。
- **P2 圆角卡片化。** X 原生把整块媒体做成「一个 8px 圆角的块 + 内部直切片」
  （实测链条：`tweetPhoto` 0、上一层包裹 `8px` + `overflow: hidden`、`ScrollSnap-List` 0），
  我们给**每一片**套 16px 圆角加 6px 缝 → 眼睛读到「4 张卡」。
  这是本项目唯一一处**明确比原生差**的规则，也是纯 CSS 一条规则就能修的。
- **P3 宽列让图变小。** 0.78 倍 + 半格切边 = 「为什么要装这个脚本？」。
- **P4 比例被破坏。** 单图压扁 40% 是硬伤，不是风格问题。
- **P5 详情页没有层级。** 焦点帖 ↔ 回复同 hairline、同字号、同操作栏，
  「帖子详情页」缺少「主角 / 会话」的编辑结构。
- **P6 语义没被读。** 6 个 emoji 被当段落排（24px 行高 + 20px 段后距），
  视觉上像「正文丢了」而不是「作者用 emoji 起题」。
- **P7 悬浮件与内容列打架。** 1280 视口下设置 FAB 压住媒体 58px。
- **P8 节奏扁平。** 所有间距在 8/12/16/24 里打转、所有过渡 180ms ——
  均匀本身就是「机器排版」的信号；编辑设计里间距要按层级分档（8/12/20/32/56）。

## 3. 「高端 / 反 AI 味」的可操作定义

**高端 = 编辑设计的三件套**：
一条**左轨**（头像列，所有内容的左缘严格对齐）、一个**版心**（阅读流的左右边界固定）、
一条**层级间距梯**（8 / 12 / 20 / 32 / 56，只有这五档，相邻层级差 ≥1.5 倍）。

**反 AI 味 = 拒绝这七种手法**（括号内是本项目的具体形态）：

1. 卡片化一切（本项目的具体形态：每片 16px 圆角 + 暗色描边）→ P2。
2. 均匀间距 + 单一动效时长（所有间距 12/16、所有过渡 180ms）→ P8。
3. 装饰性强调（渐变、玻璃拟态、emoji 当图标、彩色胶囊标签、多层阴影）。
4. 无视内容真实结构（emoji 当段落、单图当轮播、方图当横图）→ P4 / P6。
5. 把「更宽」当目标（列变宽、版心不变）→ P1。
6. 入场动画 / 视差 / 列表 stagger —— 在虚拟化时间线里回收会反复触发，只会闪。
7. 换字体族、换品牌语义色、覆盖 X 的 focus ring（`design-notes.md` 已列为红线，保持）。

**据此否掉的一个现成答案**：`ui-ux-pro-max` 的 `--design-system` 对这个需求给出
「Vibrant & Block-based + 玫红 #E11D48 + Playfair Display + 卡片/GSAP」。
对「注入 x.com 的样式层」不适用（不能换字体族、不能换品牌色、不能加卡片），
与 `design-notes.md` 里已删除的那份设计稿是同一类错误，不采纳。

## 4. 设计规范

### 4.1 轨与版心（Grid）

```
--te-rail: 48px;                 /* 头像 40 + 间距 12，沿用 X 实测 */
--te-spine: 764px;               /* 版心：16px 下 72 个字符宽（2026-09-14 实测 763.776） */
--te-bleed: 100%;                /* 媒体铺满整列，保留既有决定 */
```

- **阅读流进版心**：正文、元信息、操作栏、排序行、回复正文，全部
  `max-width: var(--te-spine)`。
- **Chrome 贴列边**：昵称行（含「…」/关注按钮）、媒体行保持整列宽 ——
  它们是「标签栏」与「图版」，不是阅读流。这条区分本身就是编辑意识。
- 效果：正文右缘 1144、媒体右缘 1342，形成**「窄文字 / 宽图版」的杂志式对照**。
  多出来的 198px 是留白，不是浪费。

### 4.2 焦点帖 = Hero（仅详情页）

- 焦点帖**去掉** `cellInnerDiv` 的 hairline；改用**结构色带**分隔会话区：
  `border-bottom: 1px solid var(--te-border)` +
  `box-shadow: 0 8px 0 var(--te-surface-sunken)`（8px 沉色带，不参与交互）。
- 焦点帖 padding：`20px 16px 16px`（回复保持 `12px 16px 8px`）——上下各多 8px 的层级差。
- 高度契约：`hero ≤ 视口 − 顶栏(53) − 16`；当前 886 < 900 但 > 847（900−53），
  即**滚到顶时最后一截被顶栏吃掉**。媒体预算改为
  `min(CONFIG.media.maxHeight, vh − 顶栏 − 300)`，让**第一条回复露出 ≥24px**（内容延续信号）。

### 4.3 内容语义分层（**2026-09-16 已移除**，留作记录）

> 「短帖大字号」开关与它的 `data-te-caption` 分类已按用户要求移除：正文回到 X 原生字号，
> `content-column.ts` 不再写这个属性。这一段保留判据本身（emoji 与短句怎么识别），
> 因为它是重做这件事时唯一需要重新推导的部分 —— 尤其「emoji 在 X 里是行内 `<img>`、
> `textContent` 长度为 0」这条，只看文本长度会把 emoji 帖误判成空帖。

在 `dom-watch` 的合并批次里给每条 `article[data-testid=tweet]` 打一个属性
（幂等、只写属性、不搬节点）：

| `data-te-caption` | 判据 | 排版 |
| --- | --- | --- |
| `none` | 无 `tweetText` | 媒体直接跟昵称行，间距 12 |
| `emoji` | `textContent.trim() === ''` 且 emoji `img` ≥ 1 | **字号 24px / 行高 1.1**，段后 8 |
| `short` | 可见字符 ≤ `shortMaxChars`(32) | **20px / 1.35**，段后 12 |
| `long` | 其余 | 16px / 1.5 / 72ch，段后 12（现状） |

标本正是 `emoji`（6 个 emoji、textContent 长度 0），回复里也有一串 emoji 的（`emoji` 类）。
这条规则让「短帖像标题 + 图、长帖像文章 + 图」，且**同一套 CSS 下内容自己决定版式**。

### 4.4 媒体

**多图（≥2 格）**

- **切片圆角归零**：删掉 `[data-testid="tweetPhoto"] { border-radius: var(--te-radius) }`，
  让 X 自己那层 8px 块圆角（`overflow: hidden`）生效。一块图就是一个块。
- 缝隙沿用 X 的 4px（实测 snap `gap: 4px`），**不再加 margin、不再加暗色 1px 边框** ——
  逐片描边在暗色下会把缝读成卡片边。
- `--te-radius: 16px` 收回给引用卡用；媒体块不入我们的圆角令牌，跟 X 的 8px 走。
- 暗色下媒体与背景的分离交给 8px 块圆角，不描边。

**竖长多图（格比例 < 0.8）**

- 行内右侧加**序号角标**「3/4」（12px、`tabular-nums`），属性由 JS 写、CSS 用
  `::after` + `attr()` 画（滚动时只改属性值，不插节点）。
- （阶段 3 可选，需裁决，未做）**主图 + 缩略条**：主图等比铺满预算高度，
  下方 48px 缩略条 + 序号；点击缩略条调用 `scrollTo` 驱动 X 自己的 snap 列表，
  不重建 DOM。这才能让「4 张竖图」在宽列上真正兑现「高端」。

**单图（1 格）**

- 铁律：**等比、不裁、不压扁**；高度超预算时**缩宽度**，不缩高度。
- 姿态与 X 自己的竖图一致（实测 236×510 等比、宽度跟着比例缩）：fit 后
  **宿主与图片同宽**，图片贴内容左缘，右侧是页面底色 —— 不能只缩图片而让宿主
  保持整列宽：那样会看到一个「比图片大的容器」和一个可见的 matte 空盒
  （2026-09-14 用户实测反馈，已按此修正）。
- 这会推翻 `design-notes.md` 的「不要对推文内部媒体做缩放 / 占位补偿」——
  见第 5 节。

### 4.5 操作栏与会话区

- `[role="group"]`：`max-width: var(--te-spine)`；
  **图标成组左对齐（`gap: 32px`）**，「浏览量」`margin-left: auto` 靠版心右缘。
  读起来是「一组操作 + 一个观测量」，而不是 6 个等距点。
- 计数保留 X 的缩写与 `tabular-nums`；不自己造「1.2k」。
- 命中区 ≥36×36 与 X 语义色 hover 保留（既有规则，未出问题）。
- 排序行收进版心：「最近」贴左缘、「查看引用」贴版心右缘。
- 回复之间保留 1px hairline；焦点帖下不再用 hairline（改用色带，见 4.2）。
- （阶段 3）作者自回连串：相邻 cell 同作者时加 `data-te-thread`，
  画一条 2px `--te-border` 左轨把回复串起来。

### 4.6 色、暗色、动效

- 只新增 1 个令牌：`--te-surface-sunken`。
  品牌语义色、字体族、focus ring 一律不动。
- 间距令牌收成 5 档：`8 / 12 / 20 / 32 / 56`（替掉现在只有 4/8/12/16/24 的扁平梯）。
  **2026-09-16 收窄**：推文样式层移除后只剩内容列的 8 / 20 两档有消费方，另三档的声明已删 ——
  要新增档位时连消费方一起加。
- 动效只允许「状态变化」：hover/active 颜色与底色（180ms，已有）、
  缩略图切换 opacity（120ms）。**不做**入场淡入、stagger、hover scale、视差。

## 5. 需要裁决的既有决议（已裁决，2026-09-14）

1. **单图 `fit` 模式**：为修 P4（方图压扁 40%），必须让被钳制的媒体元素按比例缩宽度 ——
   这是对推文内部媒体做尺寸干预，与 `design-notes.md`「不要对推文内部媒体做缩放 /
   占位补偿类调整（2026-09-08 用户决议）」直接冲突。**裁决：改为按开关分流，默认 fit**；
   旧决议被取代的理由与实测数据记在 `design-notes.md`「内容列排版」一节。
2. **竖图不再放大**：`fit` 模式下宽列不会把竖图放大（而是留白），
   与「800 宽下媒体随主列放大是用户接受的代价」相反 —— **随第 1 条一并取代**。
3. **面板开关数量**：新增开关会打掉 `verify.mjs` 里开关计数与顺序两条硬断言 ——
   **已同步改为「面板是设置注册表的纯函数」+ `EXPECTED_SETTINGS` 词汇表锁**（新增开关只改词汇表一行）。
   2026-09-15 曾拆出 `caption-scale` / `carousel-index` 两个子开关；2026-09-16 用户移除四个功能后
   面板剩 6 个开关（布局两项 + 内容四项），词汇表见 `verify.mjs`。

## 6. 落地（实际形态见第 8 节）

**config 新增**：`column.{enabledByDefault, actionGap, carouselIndex}` 与 `media.fit`。

**开关**（`registerSetting`，进页内面板，不挂油猴菜单）：

- `content-column` 内容列排版（版心 + 焦点帖 + `carousel-index` 的总闸）
- `carousel-index` 轮播序号（`3/4` 角标；关掉时 JS 连属性一起清）
- `media-fit` 单图等比（默认跟随 `media.fit`）

（2026-09-15 拆出、2026-09-16 移除的两个：`caption-scale` 短帖大字号、
`tweet-density` 推文留白 —— 见 `design-notes.md`「推文样式层为什么被移除」。）

**门禁**：见第 8 节的实测数字。

**分阶段**

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| 1（纯 CSS） | 版心收敛、多图圆角修正、间距梯 | 已落地（版心由共享令牌层提供） |
| 2（JS 属性） | 焦点帖标记、轮播序号 | 已落地（`data-te-caption` 随短帖大字号于 2026-09-16 移除） |
| 3 | 单图 `fit` / 主图 + 缩略条 / 作者自回左轨 | 只落地 `fit`，另两项未做（理由见 8.7） |

**不做**

- 不换字体族 / 品牌语义色 / focus ring。
- 不给推文加卡片、阴影、渐变、玻璃。
- 不做入场动画。
- 不为了「看起来更满」把媒体再放大 —— 宽列的正确收益是留白与版心，不是像素。

## 8. 实现记录（2026-09-14）

落地的文件与开关：

| 位置 | 内容 |
| --- | --- |
| `src/features/content-column.ts` / `.css` | 版心、焦点帖、轮播序号；开关 `content-column` + 子开关 `carousel-index`（`caption-scale` 于 2026-09-16 移除） |
| `src/features/media-cap.ts` | 单图等比 `fit` 模式；开关 `media-fit` |
| `src/features/theme.css` | 共享令牌：间距 `--te-gap-1/3`、版心 `--te-spine`、结构色带 `--te-surface-sunken`（当时叫 tweet-ui.css；另三档间距于 2026-09-16 删除） |
| `src/lib/unlock-width.ts` | 新增 `SCRIPT_SIZED_SCOPE`：放过本脚本自己定过尺寸的媒体 |
| `src/config.ts` | `column.*` 与 `media.fit` |

**与提案的偏差**（都是实测逼出来的）：

1. **版心是 px 令牌 `--te-spine: 764px`，不是 `var(--te-measure)`**：`ch` 按元素**自身**字号解析，
   操作栏继承 X 的 15px 时 `72ch` 只有 633px。当年由 JS 从真实正文元素读 `max-width` 的解析结果
   写入令牌；2026-09-16 正文限宽规则随推文新样式移除、测量失去样本，令牌回到静态 764px。
   附带结论：**不能用「量 72 个 0」反推 ch** —— 同一字体下 72 个 0 实测 785px，而 72ch 解析为 764px。
2. **版心必须带 `!important`**：X 给操作栏写死 `max-width: 600px`，宽度解锁器把它放开成
   `max-width: 100% !important`；两条都是本脚本的声明，版心用同一种手段收敛回去。
3. **操作栏保留 X 的等距分布**（放弃提案里的「图标成组左对齐 + 观测量靠右缘」）：
   X 的按钮是 `flex: 1 1 0%`，强行左聚会在详情页留出半行空白。版心只把这条轴从 946 收到 764。
4. **Hero 分隔用结构色带**（不是 cell 上的 `box-shadow`），焦点帖内边距 `20px 16px 28px`
   （= 间距 20 + 色带 8）。**色带 2026-09-17 从 `article::after` 改成 article 自己的背景**
   （`background-size: 100% var(--te-hero-band)` + `background-position: bottom left`）：
   旧的 `::after` 靠左右 -16px 负 margin 铺满整列，而负 margin 会掉进 X 的 flex 布局被
   `flex-grow` 项吸收，焦点帖内容因此比内容盒宽 32px、右侧被 article 的 `overflow:hidden`
   裁掉（实测正文 978 vs 内容盒 946）。铺满的矩形与总高度都没变。
   详见 `design-notes.md`「焦点帖 Hero 色带为什么不用负 margin」。
   **去掉下边界线要连子元素一起清**（2026-09-15 实测修正）：X 把分隔线画在 `cellInnerDiv` 的
   **首个子元素**上，`cellInnerDiv` 自己的 border 宽度是 0 —— 只写父层时这条规则从 2026-09-14
   落地起就一直没生效（真机复验：父层 `0px solid rgba(0,0,0,0)`、子层 `1px solid rgb(239,243,244)`）。
   现在父层与 `> *` 一起清，e2e 两条断言分别量父层与子层。
5. **排序行（最近 / 查看引用）未做**：它的容器没有任何稳定锚点，文案随语言变化
   （zh「最近」/ en「Latest」），拿不到可靠判据 —— 不做比做错好。操作栏与它同处一行时
   版心只作用于操作栏，视觉上仍可接受。
6. **媒体预算公式**：提案写的是 `vh − 顶栏 − 300`；当时先没动（怕牵动既有实测）。
   2026-09-14 按同一思路重定为 `clamp(vh − 320, 320, 700)`，并把结果公布成
   `documentElement.dataset.teMediaBudget` 供验证脚本读取 —— 理由、实测与「仍然低于
   600 列的那种情况（轮播）」见 `design-notes.md` 的「高度预算按视口推导」。
7. **阶段 3 只做了单图 `fit`**：主图 + 缩略条、作者自回左轨未做 —— 前者要 JS 接管滚动、
   后者要跨 cell 判作者，收益不如先把 fit 的比例问题修掉。
8. **fit 模式宿主与图片同宽、不铺 matte**（2026-09-14 用户实测反馈修正）：只缩图片会让宿主
   仍占整列宽，观感是「容器比图片大、左右一圈冗余空间」。宿主一起收窄后，X 的 8px 圆角包裹
   贴着图片，右侧留的是页面底色而不是一个空盒子。
9. **轮播内部不再是行宿主，也不进 fit**（2026-09-14 实测）：轮播格的比例盒未钳制时宽 591px
   ≥ `lockWidth`，会被误当行宿主单独钳制 → 首格 295×540、其余格 291×534、行框撑到 1010px；
   加上 X 逐格渲染，首格还会被误判成「单图」并钉住尺寸。修法见 `design-notes.md`。
10. **fit 收整条媒体链 + 不依赖 X 重排 + 宽列生效前不丢节点**（2026-09-14 用户实测反馈）：
    只缩图片与宿主时，链上更外层的包裹仍是整列宽 —— 那正是用户看到的「容器比图片大」；
    fit 现在把整条链的宽度都写死成图片宽度，并且先试 fit、成功就跳过「有没有跟着重排」的校验
    （该校验在单图上偶发失败 → 整链还原 → 刷新时好时坏）。另外补了两条兜底：宽列生效前
    到达的媒体丢弃后挂有限次重试；图片 load 时若不在已钳宿主里就重新入队。
    修后同一帖子连续 5 次加载全部落在 608×540（自然比例 1.126）。
11. **版心不再需要 `!important`**（2026-09-14）：解锁器的判据从「尺寸落在 600px 附近」
    改成「从内容单元向上遍历祖先链」后，操作栏不在候选之列，不再被打上 `max-width: 100% !important`，
    版心靠选择器特异性就能赢 X 的 `max-width: 600px`。判据的来历见
    `docs/design-notes.md`「尺寸像 ≠ 角色是」与 `docs/architecture.md` 的两条不变量。
12. **等比覆盖视频 / GIF，且判据不看宿主当前高度**（2026-09-14 实测）：GIF 帖（固有 1200×1000）
    停在 976×540 的盒子里、object-fit: contain 两侧留黑边 —— 真因是 X 的比例盒让行高**正好等于预算**，
    「自然高度 ≤ 预算 → 无需处理」把这一行直接跳过；另外播放器里的 240×240 装饰图会被当成内容。
    现在判据是「固有比例 × 行宽 > 预算」，固有尺寸取面积最大者。
13. **解锁器改为「从内容单元向上遍历」**（2026-09-14 用户实测回归）：中间那版用
    `el.querySelector(内容单元)` 判断「这是不是列容器」，踩了 X 的渲染时序 ——
    列容器先挂、推文后渲染，谓词在那一刻为 false 且祖先不会回看，
    带 `max-width:600px` 的容器始终不被标记 → **整列退回 600px**。
    现在候选由遍历方向给出，另加 dom-watch `overflow` 时整树补扫兜底。
14. **fit 钉住「媒体到宿主之间的每一层」，并解除 X 伪装成 `max-width` 的高度上限**
    （2026-09-14 用户实测回归，Ford_R_plus 竖长单图）：窄媒体被 X 逐层 shrink-wrap
    （竖长图 292×680 → letterbox 成 219×510），媒体列每层包裹都窄于 `lockWidth`，`findHost`
    抬到整行才命中宿主 → 包裹层落在宿主内部、逃出 `run`。只钉宿主与媒体时媒体盒 249×580、
    外面几层仍 219×510（含 X 的内联 `width:218.875px;height:510px`），图片从容器右下溢出
    30×70px、卡片圆角框横切图片。现在按「媒体到宿主之间的每一层」钉同一尺寸。
    同一形态还有第二层约束：X 把自己那 510px 高度上限写成**内联 `max-width`**
    （`= 510 × 固有比例`），竖长图上它会小于等比宽度 —— /home 实测 1000×1339 帖我们写
    `width:433px`、`max-width:380.8px` 把卡片卡在 381，图片溢出 52px；所以钉宽高时必须同时
    解除 `max-width` / `max-height`。解锁统一走**逐属性**原值回写：整条 `style` 快照会把链上
    元素被 X 新改的其它属性一起还原（实测宿主 `aspect-ratio` 被还原成旧值 → 行高又超预算 →
    永远解锁不掉）。
    真机复验：钉住的链（10 / 6 / 10 层）与媒体矩形逐层零差；/home 滚动 5 轮 4 个等比媒体
    （464 / 410 / 435 / 717 宽）全部闭合、不闭合计数 0。
