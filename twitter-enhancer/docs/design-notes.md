# 尺寸与设计实测结论

数值都是真机量出来的（1440 视口为主），改之前先看这段，别凭感觉调。
设计令牌与取值理由只住在这里和源码注释里 —— 早期生成过一份 `design-system/` 设计稿
（玫红配色 + Playfair Display + 卡片 / GSAP 动效），那套东西对"注入 x.com 的样式层"不适用，
已整体删除，别再重建。

## 内容区与列宽（2026-09-08 实测）

X 三栏的内容区是一个固定盒子：主列 600 + 间距 30 + 右栏 350，右栏自带 `margin-right`
（1440 视口 70px，1024/1280 视口 10px）。`/i/grok` 就是 X 自己的「单栏版」这个盒子 ——
它把右栏那份横向空间整个让给主列，**主列左缘与 `/home` 完全相同**，左导航条（fixed，275px）一点没动。

| 视口 | 三栏行左缘 | 内容区宽（= grok 主列宽） | `/i/grok` 主列 | `/home` 主列 + 右栏 |
| --- | --- | --- | --- | --- |
| 1024 | 96 | 920 − 10 = 910 | 910 @96 | 600 @96 + 290 @716 |
| 1440 | 363 | 1050 − 70 = 980 | 980 @363 | 600 @363 + 350 @993 |
| 2560 | 923 | 1050 − 70 = 980 | 980 @923 | 600 @923 + 350 @1553 |

结论：**右栏隐藏 = 主列铺满这个盒子**（`行宽 − 右栏保留的右边距`），不居中、不移左缘，
于是 `/home` ↔ `/i/grok` 切换时主区几何逐像素相同。右栏显示时才按 `CONFIG.timelineWidth`（800）封顶。

- 断点 `CONFIG.timelineBreakpoint = 1095`；视口更窄时整个功能交回 X 原生。
  不要照抄 minimal-twitter 的 988/1000px，那是它自己的两处断点。
- X 给时间线 / 推文容器写死过 600px 上限（`CONFIG.lockedWidthRange = [560, 660]`），
  落在这个区间且明显窄于主列的元素由 `src/lib/unlock-width.ts` 放开到 100%。
- 竞品（typefully/minimal-twitter）的宽度控制是纯声明式 CSS（5 档硬编码 + `@media`），
  它**不处理推文内媒体**，800 宽下超高轮播纯等比放大 —— 这是本项目 `media-cap` 存在的理由。
  可借鉴的一手：给内层包裹 `div:last-child` 打 `max-width: unset` 顶开 X 自带的内层宽度上限。

## media-cap：媒体高度钳制

现象与边界（真机实测）：

- 单图竖长图 X **自带**约 ≤510px 高度钳制，不用管。
- 真失控的是**多图横向轮播的竖长行**：800 宽列下实测行高 774~898px，加正文/操作栏必然超一屏。

做法与铁律：

- 只压**宿主行的 layout height** 到预算：`clamp(视口高 − chromeAllowance(320), minHeight(320), maxHeight(700))`
  —— 目标是让焦点帖的元信息与操作栏留在当前屏内（推导与实测见下面「高度预算按视口推导」一节）。
  轮播格带内联 `aspect-ratio`，压行高后格子会**自动等比重排**（792px 高的 2:1 行压到 540，
  格从 425×786 变成 289×534）：比例不变、无裁剪、scroll-snap 依然准确。
- **绝不要再叠加 `transform: scale`**：height 与 scale 会双重缩小成 `原高 × k²`（likes 页踩过，
  表现为图片被压到 391px + 两层负 margin 导致布局错位）。
- 冗余空白来自宿主之上的**纯媒体包裹祖先链**，里面可能有 `padding-bottom: calc(…%)` 的比例盒
  （高度 = 宽 × 组内比例，与格子无关）：链式把整条纯媒体祖先压到预算，比例盒 padding 归零，
  原值记在 WeakMap 里、解锁时还原。爬升边界：到 `article` / `cellInnerDiv` / `primaryColumn` 停，
  遇到含 `tweetText` 或操作栏 testid 也停。
- 宿主判据：从媒体元素向上找到的第一个宽度 ≥ `CONFIG.media.lockWidth = 566` 的祖先
  （把定位抬到「整行」而不是轮播里的某一格）。
- 压完做一次布局校验：内容没跟着重排（罕见：固定像素高的媒体）就立刻还原，绝不裁剪 / 重叠。
- **不要对推文内部媒体做缩放/占位补偿类调整**（2026-09-08 用户决议）：800 宽下媒体随主列放大
  是用户接受的代价，`media-lock` 那套已整体移除，别再提。
- 等比（fit）要钉的是**媒体到宿主之间的每一层**，不只是 `run`（宿主 + 宿主的纯媒体祖先）：
  X 会逐层 shrink-wrap 窄媒体 —— 竖长图（292×680）被它自己的 510 高上限 letterbox 成 219×510，
  媒体列上每一层包裹都窄于 `lockWidth`，`findHost` 只能抬到整行（978）才命中宿主，于是这些
  包裹层落在宿主**内部**、逃出 `run`（2026-09-14 用户实测 Ford_R_plus 帖：媒体盒被钉成 249×580，
  外面几层仍是 219×510，其中一层还带 X 的内联 `width:218.875px;height:510px` —— 图片从容器
  右下溢出 30×70px、卡片圆角框横切图片中下部）。判据与宿主定位无关：**媒体到宿主之间的每一层
  包裹都钉到同一尺寸**，两种形态（宿主紧贴媒体 / 宿主被窄包裹层隔开）都闭合；这类层常带 X 的
  内联宽高，解锁必须逐字还原，不能只 `removeProperty`。
- **X 用它自己的 510 高度上限伪装成内联 `max-width`**（`max-width = 510 × 固有宽高比`）：
  竖长图上它会小于按预算算出的等比宽度，于是盒子被卡住、图片溢出 —— /home 实测同一条
  1000×1339 竖图帖，我们写 `width: 433px`、X 的 `max-width: 380.8px` 把卡片卡在 381，
  图片比容器宽出 52px。所以钉宽高时必须同时把 `max-width` / `max-height` 解除
  （`none`），否则「钉了等于没钉」。解锁走**逐属性**原值回写（不是整条 `style` 快照）：
  链上元素随时可能被 X 改写别的属性（实测宿主被钳后 `aspect-ratio` 更新，整条写回把它
  一起还原成旧比例 → 行高又超预算 → 「怎么都不解锁」）。
  真机复验：Ford_R_plus 竖长图 249×580、GIF 696×580、单图 653×580，钉住的整条链（10 / 6 / 10 层）
  每层与媒体矩形**逐层零差**（dW=dH=0），连读两次一致；/home 连续滚动 5 轮共 4 个等比媒体
  （464 / 410 / 435 / 717 宽）逐层零差、不闭合计数 0。

## 解锁器与轮播格的冲突（2026-09-14 实测）

现象：推文详情页（3 张竖图的横向轮播）里竖图被放大**铺满整列宽**并裁切，观感像
「图片宽高都不再受限制」；同一页面反复冷加载时好时坏。

- X 的横向轮播（`data-testid="ScrollSnap-List"`）每一格的宽度 = **行高 × 内联
  `aspect-ratio`**：3 张竖图（原图 1521×2048，比例 0.74248）在 978 宽列、行高 757 时
  格宽 **562px**（格内 `tweetPhoto` 560px）。
- 562 正好落在 `CONFIG.lockedWidthRange = [560, 660]`（本意是抓 X 写死的 600px 容器），
  于是 `src/lib/unlock-width.ts` 把轮播格放开成 `width: 100%`（946px）。`media-cap` 只压
  行高（757 → 540），格宽仍是整列 → 竖图被放大铺满、上下裁切。
- 命中与否是**竞态**：解锁器每帧 300 节点的 BFS 先扫到该格（格宽还是 562）就中招；
  `media-cap` 的 rAF 钳制先把它压到 398（< 560）就正常。冷加载实测 8 次：4 次坏、4 次好。
- 结论：**解锁器改按角色判定**（2026-09-14 重做）—— 只有承载内容单元的容器才参与解锁，
  所以轮播格与轮播之外的写死 600px 盒子都不再被放开。当时的「轮播子树豁免」已被角色判据取代，
  见下面「尺寸像 ≠ 角色是」一条与 `unlock-width.ts` 的 `CONTENT_UNIT` 注释。

## 右下角设置按钮（2026-09-13 实测）

镜像 X 自己悬浮按钮的实时几何，读不到时用 `CONFIG.settings.fab` 兜底：
55×55、圆角 16、图标 32；与 Grok / 私信按钮同列（距右 `right: 20`）、间距 `gap: 12`；
页面没有右下角抽屉容器时（如 `/i/grok`）退回 `fallbackBottom = 146`（= Grok 收起态距底 79 + 按钮高 55 + 间距 12），
保证有 / 没有 Grok 按钮的页面位置一致、导航时不跳动。

## 脚本图标（`@icon`，2026-09-18）

管理器列表里那一枚图标此前是空的（默认白纸）。真源 `assets/icon.svg`，构建时读它、base64
内联进产物头部 —— **产物里没有图片文件，也不因此产生任何网络请求**。

画的是两根竖柱：**左窄栏 + 右宽列**，就是脚本做的两件事（主列铺满内容区、右栏让开）。

- **为什么内联而不是指向 raw 直链**：`@icon` 写 URL 时，装脚本 / 检查更新时管理器会去取它一次，
  那在 README 承诺的「纯本地、零请求」之外多出一次网络行为，且 CDN 抖一下图标就退化成默认图标。
  data URI 让产物自包含、离线安装也有图标。
- **为什么 base64 而不是 `data:image/svg+xml;utf8,<svg …>`**：Violentmonkey 2.27 会把 utf8 形式的
  data URL 判成非法 URL（violentmonkey#2214，同年 10 月修）；base64 形式没有这个坑。
  篡改猴的元数据文档也只写了「URL 或 Base64 Data URI」。
- **为什么是两根实心柱**：图标在管理器列表里只有 16~32px。候选里「细中柱 + 两侧朝外三角」
  （想表达"撑开"）在 16px 下糊成一团，且被读成媒体控制键；「描边列框 + 正文线」（想表达内容列）
  小尺寸下只剩一个方框。实心柱的轮廓各档都立得住：16px 时窄柱 1.6px、宽柱 7.9px。
- **配色**：中性墨黑 `#0F1419` 底 + 纯白图形，浅色 / 深色两套管理器主题下都够对比；
  无渐变 / 无阴影 / 不借 X 的品牌蓝（与 `content-column-design.md` 的拒收清单一致）。
- **几何**：24 网格，四周留 4px —— 部分管理器会自己加圆角 / 圆形裁切。
- **怎么验的**：headless 渲染 16 / 20 / 24 / 32 / 64 / 96px，外加「16px 栅格化后放大 8×」一栏
  对照看；再把**产物头部那条 data URI 本身**当 `<img src>` 渲染一遍，确认解码结果确实是能画的图。
  `scripts/verify.mjs` 里有断言锁住「产物里的图标 = `assets/icon.svg` 的图形部分」，
  改了 SVG 忘了重建会红。

## 高度预算按视口推导（2026-09-14 重定）

问题（用户提问「我们的高度限制是不是比默认 600 宽时还低」引出，实测 1440 宽）：

| 内容形态 | X 原生 600 列 | 旧预算（540） | 新预算（视口 900 → 580） |
| --- | --- | --- | --- |
| 单图 1200×1066 | 596×530 | 608×540 | **653×580** |
| GIF（固有 1200×1000） | 596×354 | 648×540 | **696×580** |
| 4 图竖图轮播（每格） | 356×650 | 291×534 | **313×574** |

- 旧公式 `min(540, 视口高 − 220)` 有两个缺陷：**小屏做不到一屏**（视口 720 时给 500，
  实测帖子高 855、操作栏底边 771，出屏 51px）；**大屏被常量顶死**（视口 1080/1400 时
  仍只给 540，空着 300–600px 不用）。
- 新公式按「焦点帖操作栏必须落在视口内」推导：媒体行之外上下共约 254px（实测 143 + 111），
  再留 ~66px 给更长的正文 → `视口高 − 320`；上限抬到 700，让高屏 / 竖屏拿到更大的图。
- 复测：视口 720/900/1080/1400 四档，媒体行 400/580/700/700，操作栏底边均在视口内 ✓
  （720 那档此前是唯一违反契约的）。
- **仍然低于 600 列的只剩轮播**（每格 313 vs 原生 356）。要在 900 视口下做到 650 的行高，
  操作栏会落到 935 > 900 —— 这是「一屏看全」的硬取舍，不是实现问题；
  视口 ≥1080 时新上限 700 已经让格宽（383）超过 X 原生（356）。
- 预算同时写进 `documentElement.dataset.teMediaBudget`，验证脚本直接读它，
  不再在测试里复算公式（避免公式与断言两处漂移）。

## 一轮结构性优化（2026-09-14，四项）

按「宽度覆盖类 vs 产品决策类」的分层（见 `architecture.md` 的不变量）把测量层的复杂度收掉：

1. **锁宽区间不再写死**：解锁器的主判据改为「X 原生列宽 ± 半宽」。原生列宽由
   `timeline-width.ts` 在宽列生效**前**实测（本来就要为「只放宽不收窄」读一次），
   `CONFIG.lockedWidthRange` 退化成读不到时的兜底 + 半宽来源。
   X 改断点 / 改列宽时判据跟着走，不再依赖「600」这个数字。
   **踩坑（同日修）**：第一版把「不是我们写过的宽度」当条件（`widenedByUs`），
   但 SPA 导航时上一页的 `data-te-timeline='wide'` 还在，新主列一挂载就被 CSS 写成目标宽 ——
   此刻读到的是 980（我们自己的输出），判据区间被挪到 [930,1030] → 列容器不再放开 →
   **时间线内容退回 600px 且一直坏到刷新**（用户实测反馈）。条件改成
   `teTimeline !== 'wide'`（我们自己的宽度覆盖没生效）后复测：冷加载 / SPA 到个人资料 /
   回 /home 三态都是 978。回归断言同时加在 jsdom（把新主列的实测宽度设为 980 模拟该时刻）
   与真机 e2e（真点左栏「个人资料」再回 /home，断言内容列 > 900）——jsdom 那条已验证
   「注入旧逻辑即失败」。
2. **等比的盒子高度恒取预算**：以前取 `min(预算, 宿主当前高度)`，而那个「当前高度」可能是
   X 按我们上一轮写的宽度重算出来的（比例盒按盒宽算高度）—— 等于把脚本自己的输出当输入。
   现在恒取预算；代价是竖图比 X 自带的 510px 上限略大 6%，换来判据与 X 的盒子完全解耦
   （`/home` 实测：单媒体行全部等比到 540 高，比例与原图一致）。
3. **增量路径合并成一种「种子」**：旧版按来源分成两套（新增节点走 `applyOne`、
   媒体加载完走逐宿主重算），而 `applyOne` 撞上 `media.closest('[data-te-media-capped]')`
   会直接返回 —— 「宿主里从 1 张图变成 2 张（轮播成型）」在增量路径上被漏掉。
   现在只有一种东西：种子（媒体元素或已钳宿主），帧任务里统一「解锁这条链 → 重新定位宿主 → 钳制」。
   重新定位必须**从种子里的媒体元素起算**（与首轮同一起点），否则同一条行会在
   `fitHost` / `fitWrap` 两级之间漂移（第一轮钳 A、增量重算却钳它的父层 B）。
4. **三张 WeakMap 合成一条 originals 记录**（`style` / `width` / `paddingBottom`）：
   解锁路径只有一条查询入口，加记录与还原不会再漏；`style` 用 `null` 区分
   「原本就没有这个属性」（还原时删掉，而不是写成空串）。

复验：`npm run verify` 247 项、`npm run e2e:real` 89 项全绿；真机复测（高度预算重定后）——
GIF 帖 696×580、单图帖 5 次均 653×580、4 图轮播 4 格统一 313×574、`/home` 内容列 978
（未退回 600）；残存扫描（超预算 / 非预期黑边）为 0。

## 主题与共享令牌

这一层原来叫「推文新样式 + 推文留白」，2026-09-16 按用户要求**整体移除**（连同
「短帖大字号」「导航条搜索框」）。留下的只有两件事，写在 `src/features/theme.css` + `theme.ts`：

- **主题检测**：`theme.ts` 读 `html` 的 `color-scheme`（读不到再回退 `body` 背景亮度）判出
  Light / Dim / Dark，写在 `html[data-te-theme]` 上，CSS 的主题分支消费
  （`theme.css` 的 `--te-surface-sunken`、`settings-panel.css` 的 `--te-set-*`）。
- **共享令牌**：间距令牌（当前只剩 `--te-gap-1`(8) 与 `--te-gap-3`(20) 有消费方 ——
  另三档随推文样式层一起移除，见下）、版心 `--te-spine: 764px`、结构色带 `--te-surface-sunken`。
  **只放变量声明，不放任何选择器规则** —— 这里一出现观感规则，就会重新长出一个「推文新样式」。

注入第三方站点的样式层仍然守这几条红线：**不换字体族**（X 用 TwitterChirp）、
**不换品牌语义色**（Reply `#1d9bf0` / Repost `#00ba7c` / Like `#f91880`）、
**不移除 focus ring**、只锚 `data-testid`。

## 推文样式层为什么被移除（2026-09-15 审计 → 2026-09-16 移除）

2026-09-15 的审计（方法：同一 headless profile 先量 X 原生值、再按开关矩阵量我们改后的值；
探针 `.playwright-cli/audit*-tweetui.mjs`，不入库）结论是：**这一层里与 X 原生逐值相同或
纯属叠加的部分，远多于它真正改掉的部分** —— 自绘的单元格分隔线（与 X 自己那条相邻成 2px 双线）、
引用卡框（顺手把名字行里 1em 的认证徽章撑成 42×42 方框）、`share` / `views` 两组死选择器
（现版本这两个 testid 不存在）、操作栏 hover 圆底（X 自己在更内层已经画过）都在那次被删。
剩下的部分（正文 16px/1.5/72ch、单元格 12/16/8 内边距 + 36px 命中区）才是这一层真正的改动。

2026-09-16 用户看完观感后决定把这一层整个移除，于是正文回到 X 原生的字号与不限宽，
「窄文字 / 宽图版」的对照只剩操作栏那一条 764px 版心（`--te-spine` 也从「实测 72ch 的解析值」
退回静态值，见 `content-column-design.md` §8）。

由此仍然生效的两条：**新增规则前先量 X 原生值**（同值就是复刻，别写）；
**观感类新增元素各自带开关**（现在还活着的例子只有轮播角标 `carousel-index`）。

同一次审计里发现、至今仍没做的几件事（留着，别当成已修）：

- **设置按钮在 1280 视口压住媒体右下角约 58px**（content-column-design.md 的 P7，2026-09-14 实测）。
  它是面板的入口，不做开关；真要修是「按媒体矩形自动避让」，属于独立一件事。

  它移除后只剩内容列的两处（轮播角标 8、焦点帖色带 20），2026-09-16 把那三档没有消费方的
  声明删掉了。**要新增一档时连消费方一起加**，别再先把梯子铺回去。

## 内容列排版（2026-09-14 实测，见 docs/content-column-design.md）

`src/features/content-column.ts` + `content-column.css`，开关 `content-column`；
`media-fit`（单图等比）在 `media-cap.ts` 里。标本：`Sena_8ito` 那条 4 图竖图帖。

- **版心 `--te-spine: 764px`**：操作栏收进 764px，昵称行与媒体保持整列宽。
  为什么不用 `72ch`：`ch` 相对元素**自身**字号解析，操作栏继承 X 的 15px 时 72ch 只有 633px，
  与正文的 764px 对不齐。这个值是 16px 字体下 72 个字符宽的实测取整（2026-09-14 真机 763.776px）。
  **曾经由测量层覆盖**：写 `--te-measure: 72ch` 的那一层（tweet-ui）读真实正文元素 `max-width`
  的解析值写进 `--te-spine`；2026-09-16 推文新样式整体移除后正文不再限宽、测量失去样本，
  版心回到 `theme.css` 里的静态 764px（消费方 content-column 只读令牌，不自己反推）。
  **注意不能用「量 72 个 0」反推**：同一字体下 72 个 0 实测 785px，而 72ch 解析为 764px。
- **版心不需要 `!important`**：X 给操作栏写的 `max-width: 600px` 是普通声明，本选择器的
  特异性已经高过它。曾经要压的是宽度解锁器给同一元素打的 `max-width: 100% !important` ——
  解锁器现在按角色判定（操作栏不承载内容单元），这条军备竞赛随之消失。
- **操作栏保留 X 的等距分布**：它的按钮是 `flex: 1 1 0%`，强行左聚会在详情页留出半行空白；
  版心只负责把这条轴从 946px 收到 764px。
- **内容语义（已移除）**：`article[data-te-caption] = none | emoji | short | long` 与
  emoji 24px / 短句 20px 的字号规则随「短帖大字号」一起下线（2026-09-16 用户要求）。
  留在这里的判据供将来复用：emoji 在 X 里是行内 `<img>`、`textContent` 长度为 0，
  所以「emoji 独占正文」必须靠 img 计数单独识别，不能只看文本长度。
- **焦点帖**：详情页里 `article` 内存在 `a[href]` 的路径 === `location.pathname` 的那一条
  （2026-09-14 实测：焦点帖命中、同页 45 条回复全部不命中）。它的 `cellInnerDiv` 去掉下边界线，
  改用 article 结尾的 8px `--te-surface-sunken` 色带 + 20px 上内边距把主角立起来
  （色带 2026-09-17 改成用 article 自己的背景画，理由见文末同名一节）。
- **轮播序号**：多图轮播在媒体宿主上写 `data-te-carousel="3/4"`，CSS 用 `::after` + `attr()` 画角标；
  滚动时只改属性值。**不插节点**（React 树里插节点的回收冲突风险不值得）。
- **`media.cap.fit`（默认开）**：X 用百分比 padding 比例盒把单图铺满列宽，只压宿主高度会让图片
  被拉到容器尺寸 —— 实测 `/home` 方图 900×895 渲染成 896×540（比例 1.005 → 1.66，`object-fit: fill`
  等于纵向压扁 40%）。fit 改成「按预算高度等比缩宽度」：**宿主与图片一起收到该宽度**，
  X 自己那层 8px 圆角包裹贴着图片，右侧留的是页面底色。
  这一条**推翻了此前「不要对推文内部媒体做缩放 / 占位补偿类调整」（2026-09-08）的决议**：
  当时的理由是「800 宽下媒体随主列放大」，但实测那条规则同时带来了比例破坏。
  轮播（`ScrollSnap-List` 多格）不参与 fit：格宽由内联 `aspect-ratio` 决定，压行高会自动等比重排。
  X 自己的单图也是这个套路（竖图实测 236×510、宽度跟着比例缩），所以这不是新发明，是把
  它的处理方式推广到宽列。
- **「尺寸像 ≠ 角色是」：解锁器判据从数值区间改成「从内容单元向上遍历」**（2026-09-14，第三次修正后定稿）：
  同一类误判出现过两次 —— 轮播格 562px、等比媒体链 608px，都落进 `lockedWidthRange [560, 660]`，
  被解锁器判成「X 写死的 600px 容器」并施加 `width: 100% !important`（媒体被拉成整列宽 /
  横向拉伸 1.6 倍），且命中与否取决于两个扫描谁先跑到该节点 —— 刷新后观感不同。
  两次都靠**加一条豁免**（先是轮播子树，后是脚本自写尺寸子树）—— 每来一个新场景就要再加一条。
  中间还试过「用 `el.querySelector(内容单元)` 判断它是不是列容器」，结果踩了时序：
  X 先挂列容器、再把推文渲染进去，谓词在那一刻必然为 false，而祖先扫过就不再回看 ——
  那个带 `max-width:600px` 的容器始终不被标记，**整列退回 600px**（用户实测反馈）。
  现在定下来的两条判据：
  1. **候选由「内容单元向上走祖先链」得到**（`CONTENT_UNIT` = `cellInnerDiv` /
     `article[data-testid=tweet]`）—— 角色由遍历方向保证，没有时序依赖；
     轮播格、图片链、操作栏都在内容单元内部，结构上就不可能成为候选。
  2. **禁止自反馈**：脚本自己写过的尺寸永不再作为启发式输入（`src/lib/script-sized.ts`，
     `markScriptSized()` / `isScriptSized()`）。
  两条都写进了 `docs/architecture.md` 的「不变量」；新增功能照此办理，不要再加豁免表。
- **等比对图片与视频一视同仁，判据用「固有比例 × 行宽 > 预算」**（2026-09-14 实测）：
  akaoni2gou 那条 GIF（固有 1200×1000）被放进整列宽 976×540 的盒子，`object-fit: contain`
  把画面缩到 652 宽、两侧各留 164px 黑边。改成同一套等其后是 648×540，画面贴着盒子。
  两个坑一起修掉：
  1. **不能读宿主当前高度当判据**：X 的比例盒把行高做成了**正好等于预算**（`padding-bottom: 55.33%`
     × 976 = 540 = 预算），旧实现先判「自然高度 ≤ 预算 → 无需处理」就直接返回，等比永远不生效。
     现在用 `固有比例 × 行宽` 推出「满宽下会有多高」再和预算比，不受 X 已钳高度影响；
     盒子高度**恒取预算**（`Math.max(1, round(budget))`），不读 X 的当前高度 ——
     早期版本写的是 `min(预算, 宿主当前高度)` 以保住「只缩不放」，但那个高度可能是
     X 按我们上一轮写的宽度重算出来的比例盒高度，等于拿脚本自己的输出当输入，
     同一帖会在不同加载里落到不同尺寸（见 architecture.md 的「禁止自反馈」）。
  2. **固有尺寸取面积最大者**：播放器里还挂着 240×240 之类的装饰图，按 DOM 顺序取 `img`
     会把它当成内容（宽度会算成 540）。图片看 `naturalWidth`、视频 / GIF 看 `videoWidth`。
- **宽列下 X 的媒体派生值一直是对的，「问题都是我们引入的」这个前提不成立**（2026-09-14 实测对照）：
  同一批帖子在「X 原生 600 / 宽列 980 关掉我们的钳制 / 宽列 980 全开」三态下：

  | 帖子 | X 原生 600 | 宽列 980（关我们的钳制） | 宽列 980（全开） |
  | --- | --- | --- | --- |
  | GIF（固有 1200×1000） | 596×330（比例 1.806 → **X 自己也有黑边**） | 976×540（同 1.807） | 648×540 = 画面本身 |
  | 单图（1200×1066） | 596×530（比例 1.124 ✓） | 976×867（比例 ✓，但高 867 > 一屏） | 608×540 |
  | 4 图轮播 | 每格 356×650 | 每格 581×1063 | 每格 291×534 |

  结论：X 的媒体尺寸是**纯比例驱动**的，换宽度后比例永远正确（它不需要「重算」）；
  宽列真正的代价只有两种 —— ① X 把列宽烘焙成常量（600px 上限，见 architecture.md 的不变量）；
  ② 我们要求「一屏内看完」，而 X 没有这个约束（于是媒体被放大到超一屏，GIF 的 16:9 容器留黑边）。
  另外**对它 dispatch `resize` 没有任何作用**（上表「关钳制」与「关钳制+resize」逐像素相同），
  「让 X 自己重算」这条路不存在。
- **等比要把「盒内嵌套的播放器」一起钉住**（2026-09-14 实测）：X 把 `videoPlayer` 嵌在 `tweetPhoto`
  里，播放器的高度来自 X 那层「按盒宽算高度」的比例盒（`padding-bottom: 55%`）——
  我们收窄盒子后它会跟着变小。实测同一个 GIF 帖在 **648×540 / 648×359 / 648×0**
  三种状态之间飘（取决于谁先落笔：我们写尺寸 or X 重渲染比例盒）。
  中间试过「把内部比例盒的 padding 归零」，反而在「比例盒是唯一高度来源」时把整块压成 0；
  最终做法是**把盒内所有 `MEDIA_SELECTOR` 元素也钉成同一个盒子**（`tweetPhoto` 与 `videoPlayer`
  都是 648×540），播放器尺寸从此与 X 的比例盒无关。修后连续 3 次加载稳定 648×540。
- **fit 收的是整条媒体链，不只是宿主**（2026-09-14 用户实测反馈）：只缩图片与宿主时，
  链上更外层的包裹仍是整列宽 —— 看到的正是「包裹图片的容器比图片宽出一大截」。
  实测链条（nosir_onadat 单图帖）：`tweetPhoto` 608×540、它上面两层 976×540。
  现在 `run`（宿主 + 宿主之上的纯媒体祖先）里每个元素的宽度都写死成图片宽度，
  盒子才真正贴着图片。
- **fit 不依赖 X 的重排**：媒体盒子与整条链的尺寸都由原图比例算出来，所以 `applyCap` 里
  先试 fit、成功就直接返回，不再跑「内容有没有跟着重排」的校验（该校验在单图上是 8 次实测里
  偶发失败 → 整链还原 → 同一页面刷新时好时坏）。图片自然尺寸还没就绪时仍走老路径。
- **宽列生效前到达的媒体不能再丢**（2026-09-14 实测，同一单图帖连续 5 次刷新）：
  脚本 document-start 就位时 `data-te-timeline` 还是 undefined，X 首屏推文的媒体往往在这之前
  到达；那一刻 `isActive()` 为 false，节点被丢弃后再没有任何事件补扫 —— 5 次里 2~3 次停在
  原生 976×867。现在两条兜底：丢弃时挂有限次重试（最多 ~5s，宽列一生效就整树补扫）；
  图片 load 时若不在任何已钳宿主里，把承载它的媒体元素重新丢回增量池再试一次。
  修后连续 5 次加载全部落在 608×540。
- **轮播内部不作为行宿主**（2026-09-14 实测，Sena 4 图帖）：轮播某格的「比例盒」在未钳制
  状态下宽 591px ≥ `lockWidth 566`，会被当成行宿主单独钳制（该格高 540），其余格由行宿主
  钳制后是 534 —— 同一轮播里首格比其它格大一圈，行框还被撑到 1010px。
  `findHost` 现在跳过 `ScrollSnap-List` 的子孙（轮播列表自身仍可作宿主），
  `fitApplies` 也改判「媒体自己是否在轮播里」而不是「宿主内部有没有轮播」——
  X 逐格渲染时宿主可能**就是**某张格，轮播在它的祖先里。
- **长文（Article）正文里的媒体整体排除**（2026-09-17 用户实测反馈「文章页面，文章无法
  完整显示」，标本 `/yupi996/status/2100405798681862604`，1440 视口）：X 的长文阅读视图
  （`article[data-testid="twitterArticleReadView"]`）里**没有** tweetText 锚点，于是
  「宿主 = 媒体向上第一个够宽且**不含正文**的祖先」这条判据在这里失效 —— 正文图片的行宿主
  被正常选中（实测写前 oh=653，躲过了「超过 2.5 屏不是媒体区」那条保护），而钳制时那条
  **祖先链**（宿主 → … → article/cellInnerDiv 为止）上挂着承载**整篇正文**的容器
  （实测 158 个子块、写前 oh=23177），被写成 `height: 580px`。后果：正文从盒子里溢出，
  虚拟列表按被压短的 cell（1401px）摆放后续位置 → 回复盖在文章上、文章读不全
  （docH 4444；正常 24590+，X 原生 600 列下 20175）。
  现在 `findHost` 对 `SEL.articleReadView` 里的媒体直接返回 null：正文是**文档**，不是推文的
  媒体行 —— 与「轮播内部不作为宿主」同属结构排除（判据是稳定 testid，不是尺寸或高度）。

## 焦点帖 Hero 色带为什么不用负 margin（2026-09-17 实测）

起因：用户报「文章页面，文章无法完整显示」。同一次排查里查出**两条独立缺陷**，
媒体钳制那条记在上面「长文（Article）正文里的媒体整体排除」，这条是另一条。

- 旧实现是 `article[data-te-hero]::after` + `margin: var(--te-gap-3) -16px 0`：靠左右各
  -16px 负 margin 吃掉 article 的内边距，让 8px 色带铺满整列。
- **负 margin 会掉进 X 的 flex 布局**（X 给焦点帖内容用的是 flex 容器，内容外层是
  `flex-grow` 项）：负 margin 让这一行的「自由空间」凭空多出 32px，被 `flex-grow` 项吸收 ——
  实测 1440 视口（`/leijun/status/2100538193041142162`）焦点帖**正文 380..1358 = 978px**，
  而内容盒只有 **946px**（article 978 − 左右各 16）；正文右侧 16px 落在 article 的
  `overflow:hidden` 之外，**被裁掉**。长文页更狠：整篇正文的容器被撑到 978，右侧同样被裁
  （截图里右侧文字缺半个字）。单变量验证：运行时把那条 `::after` 设成 `display:none`，
  正文立刻回到 946。
- 现在色带画在 article 自己的背景上：`background-image` 用 `--te-surface-sunken` 的单色
  `linear-gradient` + `background-size: 100% var(--te-hero-band)` + `background-position: bottom left`，
  高度由 `padding-bottom: calc(var(--te-gap-3) + var(--te-hero-band))` 留出。
  铺满的矩形与旧实现**完全相同**（padding box = 内容盒 946 + 左右 16 = 978），
  但背景不参与 flex 布局，总高度也不变（间距 20 + 色带 8 = 28px）。
- 色带高度收进共享令牌 `--te-hero-band`（消费方只有这一条规则，见 `features/theme.css`）。
- **本文档与 `content-column-design.md` 里 2026-09-14 那批「媒体行 978」是在泄漏期间量到的**：
  焦点帖内容的真实宽度是内容盒 **946**（与 X 原生一致 —— X 原生 600 列下焦点帖媒体行就是
  内容宽 566）。列宽 978 本身没变，变的是「列里的内容不再溢到 article 的 16px 内边距上」。
